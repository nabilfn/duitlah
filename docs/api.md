# API Conventions

## Versioning

All endpoints are versioned under `/api/v1`. Breaking changes get a new
version prefix rather than mutating `v1` in place.

## Response format

Successful responses return the resource/DTO directly (no envelope).

Errors always return this shape, produced by
`com.duitlah.api.common.error.GlobalExceptionHandler`:

```json
{
  "code": "BILL_NOT_READY",
  "message": "Two receipt items have not been allocated.",
  "details": {
    "unclaimedItems": 2
  }
}
```

- `code` — stable, machine-readable, safe to branch on in frontend code.
- `message` — safe to show directly to end users.
- `details` — optional structured context. Never a stack trace.

To throw a domain error, throw `ApiException` (or a subclass like
`NotFoundException`/`ForbiddenException`) from
`com.duitlah.api.common.error` with an HTTP status, a `code`, and a
user-safe `message`. Anything else (unchecked framework exceptions, bugs)
is caught by the fallback handler, logged server-side with full detail,
and returned to the client as a generic `INTERNAL_ERROR` — never a stack
trace.

## Frontend consumption

`apps/web/src/lib/api-client.ts` wraps `fetch` and throws
`ApiRequestError` (carrying the parsed `ApiError`) on any non-2xx
response, so calling code can catch one error type regardless of endpoint.

`apps/mobile`'s `core/api/api_client.dart` (Phase 9.5) is the same
contract reimplemented over Dio: same base-URL convention, same
`ApiError`-shaped exception (`AppException`), same refresh-and-retry
behavior on 401 — see [architecture.md](architecture.md)'s Mobile section
and [security.md](security.md). Both clients hit the identical `/api/v1`
surface; nothing in this document is mobile-specific.

## Documentation

OpenAPI docs are generated by springdoc and served at `/v3/api-docs` and
`/swagger-ui.html` when the API is running.

## Idempotency

**Implemented server-side as of Phase 14** — closing a gap this doc had
carried since Phase 6. Any `POST`/`PUT`/`PATCH` request that carries an
`Idempotency-Key` header is deduplicated by `IdempotencyFilter`
(`common/idempotency/`, wired into the Spring Security filter chain right
after JWT auth), scoped per-`(userId, Idempotency-Key)`:

- The first request atomically claims the key in Redis (24-hour TTL)
  before it reaches the controller.
- A second request with the same key, while the first is still running,
  gets back `409 DUPLICATE_REQUEST_IN_PROGRESS` immediately — no business
  logic runs twice.
- Once the first request finishes, its exact response (status + body) is
  cached and replayed verbatim to any later request with that key — the
  caller gets the original result, never a second write.
- A `5xx` response releases the claim instead of caching it, so a
  genuinely failed request can be retried with the same key.

It's a blanket filter rather than per-endpoint wiring: it only ever
activates when the caller actually sends the header, so it changes
behavior exactly for the requests that ask for it (`apps/mobile` already
sends `Idempotency-Key` on finalize, settlement payments, transactions,
and goal contributions) and nothing else. `IdempotencyFlowTests` verifies
this under genuine concurrent load — 5 threads racing the same key
produce exactly one real transaction, not five.

`POST /api/v1/recurring-transactions` (Phase 10) is covered by the same
filter the instant a caller sends the header — the remaining gap is only
that `apps/mobile` doesn't yet send `Idempotency-Key` on that one call, a
client-side follow-up, not a server-side one.

`POST /api/v1/ai/chat` and `POST /api/v1/ai/affordability` (Phase 12) are
POST but deliberately excluded from the above — neither one writes
anything. Both are read-only computations (a chat turn, an affordability
check) with no side effect a retry could duplicate, so there's nothing
for an `Idempotency-Key` to protect.

## AI assistant

`POST /api/v1/ai/chat` is stateless server-side: the client resends the
full prior conversation (`history`) on every call rather than the backend
persisting a session, so there's no chat-history table and nothing to
clean up. `ChatResponse.available` is `false` whenever no AI provider is
configured (`duitlah.ai.chat.anthropic-api-key` unset) — `reply` is still
a real, honest message in that case, never a fabricated answer; see
[architecture.md](architecture.md) and
[database.md](database.md) for the "Finance Query Layer" design that
keeps the model from ever reaching arbitrary data. `POST
/api/v1/ai/affordability` has no such fallback state to represent — it
always returns real computed numbers, with or without an AI provider
configured, since it never actually calls one (see
[database.md](database.md)'s AI assistant design decisions section).

**V2 Phase 12** (see [ai-assistant-v2.md](ai-assistant-v2.md)) widened
both endpoints without changing their shape in a breaking way.
`ChatRequest` gained an optional `activeSpaceId` — omit it (or pass
nothing) for a Personal-only conversation; pass a `BUSINESS` space the
caller belongs to and Business tools (P&L, balance sheet, cash flow,
receivables/payables, overdue invoices, inventory, SST/e-Invoice
readiness, reconciliation status) become available for that request
alongside Personal and Shared (Groups/Bagilah/Settlements) tools, which
are always available regardless. An invalid or foreign `activeSpaceId`
falls back to Personal+Shared rather than failing the request.
`AffordabilityResponse` gained `upcomingBillsTotal`, `debtRepaymentsTotal`,
and `totalObligations` (the sum actually used in the `canAfford` check,
alongside `totalOwedToOthers`), plus informational-only
`averageCreditUtilization` (a 0-1 ratio, `null` with no credit cards),
`totalSavingsGoalsRemaining`, and `budgetRemainingThisPeriod` — none of
the original fields were removed or renamed.

## Subscriptions

`GET /api/v1/subscriptions/me` and `POST /api/v1/subscriptions/verify`
(Phase 13) follow the same error-code convention as everywhere else:
`GROUP_LIMIT_REACHED`/`RECEIPT_SCAN_LIMIT_REACHED` (403, thrown by
`GroupService`/`ReceiptScanService` before the write, not by this
controller) and `PURCHASE_VERIFICATION_FAILED` (400) are all stable codes
a client can branch on, with a `message` that's already written to be
shown directly to the user (see [database.md](database.md)'s Subscriptions
design decisions section for why every purchase currently fails
verification honestly rather than succeeding). `apps/mobile` catches the
first two specifically to show an upgrade dialog instead of a generic
error snackbar — see [architecture.md](architecture.md)'s Phase 13
section.

## Feedback (Phase 15)

`POST /api/v1/feedback` creates one append-only row for the
authenticated user (`category` — `BUG`/`FEATURE_REQUEST`/`GENERAL`/
`COMPLAINT` — and a free-text `message`, max 2000 chars). `GET
/api/v1/feedback/me` lists only the caller's own submissions, newest
first — there is no admin-facing list/export endpoint yet; this is only
the submission half of "feedback system" (Phase 15's own scope).

## Financial Spaces (V2 Phase 1)

`GET /api/v1/spaces` lists every `FinancialSpace` the caller is an active
member of. `GET /api/v1/spaces/{spaceId}` and `GET
/api/v1/spaces/{spaceId}/business-profile` both return `404
SPACE_NOT_FOUND` for a non-member — same "never confirm another user's
data exists" convention as every other ownership-scoped lookup in this
API. `POST /api/v1/spaces/business` (201) creates a `BUSINESS`-typed
space and its `BusinessProfile` in one call, with the caller becoming its
`OWNER`; only `name`/`legalName` are required. See
[financial-spaces.md](financial-spaces.md) for the full model and why
this is deliberately the only new surface this phase adds.

## Duitlah AutoTrack, statement import, Receipt Vault (V2 Phase 2)

`GET /api/v1/autotrack/candidates?status=` lists a user's suggested-but-
not-yet-real transactions (defaults to every status if omitted); `POST
.../confirm` (body: a `CreateTransactionRequest`, the same shape a manual
"Add transaction" sends), `.../reject`, and `.../merge` are the only three
ways one ever leaves `PENDING` — `merge` 400s with `NOT_A_POSSIBLE_DUPLICATE`
if the candidate was never flagged, and every one of the three 409s with
`CANDIDATE_ALREADY_RESOLVED` if called on a candidate that's already
`CONFIRMED`/`REJECTED`/`DUPLICATE`. `POST /api/v1/statement-imports?accountId=`
(multipart `file`) uploads a CSV/XLSX/PDF bank statement export and 400s
`UNSUPPORTED_FILE_TYPE` for anything else. `POST
/api/v1/receipts/vault?purpose=&folder=&tags=` (multipart `files`, one or
more) uploads to the Receipt Vault — a purpose-tagged, folder/tag-
searchable receipt store independent of Bagilah's own `/api/v1/receipts/scans`
flow, which this phase leaves completely unchanged. See
[autotrack.md](autotrack.md) for the full endpoint list and design
reasoning.

## Personal Bills, Loans, Credit Cards, Net Worth, Financial Health, Exports (V2 Phase 3)

`GET/POST /api/v1/personal-bills`, `.../mark-paid` (creates a real linked
expense transaction), `.../skip` — status transitions
(`UPCOMING`/`DUE`/`OVERDUE`) are scheduler-driven, not client-set. `409
BILL_ALREADY_RESOLVED` if already `PAID`/`SKIPPED`. `GET/POST
/api/v1/liabilities`, `.../payments` (optionally creates a linked expense
transaction if `accountId` is given). `PUT/GET
/api/v1/accounts/{id}/credit-card-details` — `400
NOT_A_CREDIT_CARD_ACCOUNT` for a non-card account; `currentOutstanding`/
`availableCredit`/`utilization`/`statementBalance`/`minimumPaymentDue` are
all computed on every read. `GET /api/v1/net-worth`,
`POST/GET /api/v1/net-worth/snapshots`,
`POST/GET/DELETE /api/v1/net-worth/other-assets`. `GET
/api/v1/financial-health` — `score`/`components`/`recommendations`, never
a credit score. `GET
/api/v1/exports/{transactions,bills,loans,net-worth,budgets}?format=CSV|XLSX|PDF`
and `GET /api/v1/exports/archive` (a ZIP) — real file downloads
(`Content-Disposition: attachment`), not JSON. See
[personal-gap-closure-ii.md](personal-gap-closure-ii.md) for the full
design reasoning, including why credit cards extend `accounts` rather
than becoming a second liability record, and why the score's components
are individually weighted and explained rather than one opaque number.

`POST /api/v1/budgets` gained optional `cycleType`
(`CALENDAR_MONTH`/`PAYDAY`/`CUSTOM`) and `periodStartDate`/
`periodEndDate` fields — omitting `cycleType` keeps the exact pre-Phase-3
behavior (`periodYear`/`periodMonth` required). `POST
/api/v1/transactions` gained optional `originalCurrency`/`originalAmount`/
`exchangeRate` — a display snapshot only; `amount` is always the real
base-currency figure. `GET/POST /api/v1/notifications`,
`.../unread-count`, `.../{id}/read` — the real notification backend
replacing the Phase 9.5 placeholder (in-app and email channels are live
today; push is honestly not configured yet, see
[personal-gap-closure-ii.md](personal-gap-closure-ii.md)).

## Personal Tax Centre (V2 Phase 4)

`GET/POST/DELETE /api/v1/personal-tax/income`; `GET/POST
/api/v1/personal-tax/pcb` (recording the same YA+month again updates it —

/api/v1/personal-tax/relief-candidates`, `.../confirm` (clamped to the

already confirmed/rejected; `GET/DELETE
/api/v1/personal-tax/confirmed-reliefs`; `GET
/api/v1/personal-tax/calculation` — `404 TAX_YEAR_NOT_CONFIGURED` for an
unseeded Year of Assessment, otherwise every intermediate figure in the

/api/v1/personal-tax/filing-readiness`; `GET
/api/v1/personal-tax/preparation-summary` (a real PDF download, reusing
`exports.PdfExportWriter`). See
[personal-tax.md](personal-tax.md) for the full design reasoning and an

## Business Core (V2 Phase 5)

Every endpoint below is scoped under `/api/v1/spaces/{spaceId}/...` and
requires active membership in that space; writes additionally require
the acting member's role to carry the relevant `BusinessPermission` —
otherwise `403 INSUFFICIENT_PERMISSION`, distinct from the `404` a
non-member gets. See [business-core.md](business-core.md) for the role→
permission matrix and the full design reasoning.

Team: `GET/POST /api/v1/spaces/{spaceId}/members` (`404 USER_NOT_FOUND`/
`409 ALREADY_A_MEMBER` on add), `PATCH/DELETE
.../members/{memberId}` (`409 LAST_OWNER` demoting/removing the sole
owner). Customers/Suppliers: `POST/GET/PUT/DELETE
.../customers[/{id}]` and identical routes under `.../suppliers` (delete
archives, never hard-deletes). Products: `POST/GET/PUT/DELETE
.../products[/{id}]`. Business accounts: `POST/GET/PATCH
.../business-accounts[/{id}]`, `GET/POST .../business-accounts/{id}/entries`,
`POST .../business-accounts/{id}/transfer` — balance is always a computed
response field, never a request field. Expenses: `POST/GET
.../expenses[/{id}]`, `GET/POST .../expenses/{id}/payments` — recording a
payment posts a matching business-account ledger entry and may flip the
expense's stored `status` to PARTIALLY_PAID/PAID. Sales: `POST/GET/PATCH
.../quotations[/{id}][/status]`, `POST
.../quotations/{id}/convert-to-invoice` (`409 QUOTATION_NOT_ACCEPTED` if
not yet accepted); `POST/GET/PATCH .../invoices[/{id}][/status]`,
`GET/POST .../invoices/{id}/payments` (`409 INVOICE_VOID` against a
voided invoice) — the response's `effectiveStatus` (not `status`) is the
field to display, since PARTIALLY_PAID/PAID/OVERDUE are computed, never
stored; `POST/GET .../credit-notes[/{id}]`, `POST
.../credit-notes/{id}/void`. Dashboard: `GET
.../business-dashboard` — cash position, receivables, payables, and
entity counts, all recomputed on every request.

## Business Accounting Engine (V2 Phase 6)

Also under `/api/v1/spaces/{spaceId}/...`, same membership/permission
rules as above (writes require `MANAGE_BOOKS`; reading journal entries
and every report requires `VIEW_REPORTS`). See
[accounting-engine.md](accounting-engine.md) for the full design
reasoning.

`POST .../accounting/chart-of-accounts/seed-defaults` (`409
CHART_OF_ACCOUNTS_ALREADY_SEEDED` on a second call); `POST/GET/PUT/
DELETE .../accounting/chart-of-accounts[/{id}]` (`409
ACCOUNT_CODE_ALREADY_EXISTS`; delete archives, never hard-deletes);
`POST/GET .../accounting/periods` (`409 ACCOUNTING_PERIOD_OVERLAPS`),
`POST .../periods/{id}/close`; `POST/GET
.../accounting/journal-entries[/{id}]` — posting a manual entry
requires ≥2 lines and rejects with `409 JOURNAL_ENTRY_NOT_BALANCED` if
debits ≠ credits, `409 ACCOUNTING_PERIOD_CLOSED` if the date falls in a
closed period, or `409 LEDGER_ACCOUNT_ARCHIVED` if a line references an
archived account; `GET .../accounting/reports/general-ledger` (per
account, with a running balance), `.../trial-balance`,
`.../income-statement`, `.../balance-sheet`, `.../cash-flow`; `GET
.../accounting/exports/{trial-balance,income-statement,balance-sheet}`
(CSV/XLSX/PDF, `?format=`). Two mapping endpoints live on their owning
modules rather than on `accounting` itself: `PATCH
.../business-accounts/{id}/chart-of-accounts-mapping` and `PATCH
.../expenses/{id}/chart-of-accounts-mapping` — setting either is what
lets the corresponding "record payment"/"receive payment" action start
posting a real journal entry automatically.

## Reconciliation (V2 Phase 7)

Also under `/api/v1/spaces/{spaceId}/...`; every write requires
`MANAGE_BANKING`. See [reconciliation.md](reconciliation.md) for the
full design reasoning.

`POST /api/v1/spaces/{spaceId}/reconciliation/statement-imports`
(multipart — `businessAccountId` query param + `file` part) auto-opens a
reconciliation session on a successful parse; `GET
.../statement-imports` and `GET .../statement-imports/{id}/lines` list
what was parsed. `GET .../statement-imports/{id}/lines/{id}/suggestions`
is the matching engine's output for one line (EXACT/PROBABLE candidate
ledger entries). The four line-level actions: `POST
.../lines/{id}/match` (`409 LEDGER_ENTRY_ALREADY_ALLOCATED`), `POST
.../lines/{id}/create-transaction`, `POST .../lines/{id}/ignore`, `POST
.../lines/{id}/split` (`409
SPLIT_PORTIONS_DO_NOT_SUM_TO_LINE_AMOUNT`) — all four reject with `409
STATEMENT_LINE_ALREADY_RESOLVED` if the line isn't still `UNMATCHED`.
`GET/POST /api/v1/spaces/{spaceId}/reconciliation/sessions[/{id}]`, `GET
.../sessions/{id}/summary` (line-status counts plus the current ledger
balance and, once set, the statement's own ending balance and the gap
between them), and `POST .../sessions/{id}/resolve-difference` — the
one session-level action, posting an adjustment ledger entry for any
non-zero gap and completing the session.

## Inventory & Costing (V2 Phase 8)

Also under `/api/v1/spaces/{spaceId}/...`; every write requires
`MANAGE_PRODUCTS`. See
[inventory-and-costing.md](inventory-and-costing.md) for the full
design reasoning.

`POST/GET /api/v1/spaces/{spaceId}/products/{productId}/movements`
records/lists stock movements (`400 ZERO_QUANTITY`, `400
UNIT_COST_REQUIRED` on an inbound movement missing a cost); `GET
.../products/{productId}/valuation` returns the current computed
quantity on hand, Weighted Average Cost, and total value. `POST/GET
.../products/{productId}/recipe` and `DELETE .../recipe/{itemId}` manage
a product's ingredient list (`400
PRODUCT_CANNOT_BE_ITS_OWN_INGREDIENT`, `409
RECIPE_ITEM_ALREADY_EXISTS`); `GET .../recipe/cost` returns the computed
unit cost, selling price, gross margin, and gross margin percent. `GET
/api/v1/spaces/{spaceId}/inventory/stock-valuation` lists every tracked
product's current valuation; `GET
/api/v1/spaces/{spaceId}/inventory/cogs?from=&to=` totals Cost of Goods
Sold for a date range. `CreateProductRequest` (Phase 5) gained
`description`, `cost`, `taxClassification`, `trackInventory`, and
`reorderPoint`.

## Fixed Assets (V2 Phase 9)

Also under `/api/v1/spaces/{spaceId}/...`; every write requires
`MANAGE_BOOKS`. See [fixed-assets.md](fixed-assets.md) for the full
design reasoning.

`POST/GET /api/v1/spaces/{spaceId}/assets[/{id}]` create/list/get the
asset register; `PUT .../assets/{id}` updates it (`409
ASSET_FINANCIALS_LOCKED` if cost/salvage value/useful life/method/
acquisition date are changed after any depreciation has posted — name
and category stay editable regardless). `POST
.../assets/{id}/depreciation/run` posts one period's depreciation
(`409 PERIOD_ALREADY_DEPRECIATED`, `409 ASSET_FULLY_DEPRECIATED`, `409
ASSET_ALREADY_DISPOSED`); `GET .../assets/{id}/depreciation-entries`
lists what's been posted. `POST .../assets/{id}/dispose` removes the
asset from the books in one balanced journal entry (`400
PROCEEDS_ACCOUNT_REQUIRED` if proceeds are non-zero but no business
account was given to receive them; `409 ASSET_ALREADY_DISPOSED` if
already disposed).

## Business Tax & e-Invoice (V2 Phase 10)

See [business-tax-and-einvoice.md](business-tax-and-einvoice.md) for
the full design reasoning.

`GET/PUT /api/v1/spaces/{spaceId}/business-profile` — the `PUT` is new
this phase (Phase 5 only ever let it be set once, at space-creation
time); requires `MANAGE_BOOKS`, same as the three read endpoints under
`.../business-tax/{sst-rates,sst-report,einvoice-readiness}` (each
just requires membership, since they're reports/reference data, not
mutations). `POST /api/v1/spaces/{spaceId}/invoices/{invoiceId}/einvoice/{prepare,submit,sync-status,cancel,reject}`,
`GET .../einvoice[/logs]` — all writes require `MANAGE_SALES_DOCUMENTS`.
`prepare`: `400 INVOICE_NOT_ISSUED`, `400
EINVOICE_SELLER_TIN_MISSING`/`EINVOICE_BUYER_TIN_MISSING`, `409
EINVOICE_ALREADY_IN_PROGRESS`. `submit`/`sync-status`: `409
EINVOICE_NOT_READY`/`EINVOICE_NOT_SUBMITTED`, `503
EINVOICE_PROVIDER_UNAVAILABLE` whenever no real MyInvois credentials
are configured — this is the expected, honest response in every
environment until a space configures `duitlah.myinvois.enabled=true`
plus real credentials, never a fabricated success. `cancel`/`reject`:
`409 EINVOICE_NOT_VALID`, `409 EINVOICE_WINDOW_EXPIRED` (72 hours from
validation).

## Advanced Automation (V2 Phase 13)

See [advanced-automation.md](advanced-automation.md) for the full
design reasoning.

`POST/GET /api/v1/transaction-rules`, `PUT/DELETE
/api/v1/transaction-rules/{ruleId}` — a rule's own CRUD surface;
`autotrack.CategorySuggestionService` consults these automatically,
there's no separate "apply rules" call. `POST/GET
/api/v1/spaces/{spaceId}/recurring-invoices`, `GET/DELETE .../{id}`,
`PATCH .../{id}/active` (`{"active": false}` to pause) — every
materialized invoice is `DRAFT`, found alongside manually-created ones
at the existing `GET /api/v1/spaces/{spaceId}/invoices`, distinguished

/api/v1/receipts/vault/{receiptId}/match-suggestions` — advisory only,
same shape as reconciliation's own suggestions endpoint; attaching
still goes through the existing `POST .../attach`. `POST
/api/v1/personal-bills/{billId}/receipt?receiptId=` — verifies the
receipt belongs to the caller (`404 RECEIPT_NOT_FOUND` otherwise) before
linking it. `POST
/api/v1/spaces/{spaceId}/reconciliation/statement-imports/{importId}/auto-match`
— returns `{matchedCount, skippedCount}`; auto-applies only lines with
exactly one EXACT suggestion, same audit trail as a manual match. `GET
/api/v1/notification-rules` returns all five types including ones the
caller has never touched (a computed default, not a stored row); `PUT
/api/v1/notification-rules/{type}` upserts one.

## Account deletion (Phase 15)

`DELETE /api/v1/users/me` permanently deletes the authenticated user
after confirming their current password in the request body
(`{"password": "..."}`) — `401 INVALID_CREDENTIALS` on a mismatch, the
same code `POST /api/v1/users/me/change-password` already uses for the
same failure. If the account currently owns any active (non-archived)
group, the request is rejected with `409 OWNS_ACTIVE_GROUPS` instead —
see [database.md](database.md)'s Public launch design decisions section
for why (`groups.owner_user_id` cascades, so deleting the owner would
otherwise delete the whole shared group out from under every other
member). A successful deletion also clears the caller's refresh cookie,
the same as `POST /api/v1/auth/logout`.

## Final hardening (V2 Phase 14)

`POST /api/v1/settlements/{settlementId}/payments` returns `409
PAYMENT_EXCEEDS_REMAINING` when the requested amount is greater than the
unpaid balance. The check holds a database lock on the settlement, so
concurrent requests cannot both spend the same remaining amount. The
controller-derived OpenAPI contract remains at `GET /v3/api-docs`; see
[final-hardening.md](final-hardening.md).

## Monthly Wrapped

`GET /api/v1/wrapped/promo` — the Home promo card's data source; reads
only what already exists, never generates as a side effect. `GET
/api/v1/wrapped` — every completed month's Wrapped, newest first,
`personaId`/`personaName` null for a month judged insufficient. `GET
/api/v1/wrapped/{year}/{month}` — the full story payload, generated
lazily on first request if the nightly scheduler hasn't already; `400
MONTH_NOT_COMPLETED` for the current or a future month. `POST
/api/v1/wrapped/{year}/{month}/viewed` — marks a month viewed. See
[monthly-wrapped.md](monthly-wrapped.md).
